# H2 write_all stall investigation

## Problem

H2 roundtrip latency shows a sharp cliff at 16385B (> 1 DATA frame):
- 16384B: 22µs
- 16385B: 87ms (3700x slower)

## Root cause

When a multi-frame payload triggers a WINDOW_UPDATE, the 13-byte WINDOW_UPDATE frame is flushed as a standalone TCP write. This standalone small write takes ~43ms in the H2 task context despite raw TCP write_all(13B) completing in ~3µs.

## Prototype findings (`examples/uring_submit_bug.rs`)

| Test | Pattern | Stalls? |
|------|---------|---------|
| 1 | Raw write 13B | No (6µs) |
| 2 | 64KB then 13B sequential | No (37µs) |
| 3 | Spawned writer via poll_fn | Yes (2ms) |
| 6 | Reader wakes writer (H2 pattern) | Yes (2-10ms) |
| 7 | 64KB+13B in single write | No |

**Test 7 proves the fix: batch WINDOW_UPDATEs into the same write_all as DATA frames.**

## Why batching is hard

The WINDOW_UPDATE is generated by `release_capacity()` which runs in the handler task BETWEEN receiving data and sending the response. The io_flush_loop runs as a separate task. On a single-threaded runtime, when `release_capacity` calls `wake_io`, the io_flush_loop gets a turn before the handler calls `send_data`. At that point, only the WINDOW_UPDATE is in write_buf.

Attempted fixes:
1. **Move WINDOW_UPDATE encoding to flush_write_buf** — works for batching, but wake_io still triggers standalone flush
2. **Remove wake_io from release_capacity** — fixes perf but breaks receive-only flow control (deadlock)
3. **Conditional wake_io** (only if write_buf empty) — release_capacity always sees empty write_buf since handler hasn't called send_data yet
4. **data() Pending wake_io** — fires in the echo pattern too (between chunks)
5. **poll_fn check for has_pending_window_updates** — correct but io_flush_loop can't distinguish "handler will send data soon" from "receive-only flow"
6. **Yield before flush** — can't predict how many yields the handler needs
7. **Drain loop** — infinite loop in streaming scenarios

## Correct fix direction

The architecture needs to prevent the io_flush_loop from flushing while the handler is still processing. Options:
- **Coalesce timer**: delay flush by ~1ms to let handler finish (adds latency)
- **Handler-driven flush**: don't use wake_io at all; have send_data/send_response flush directly
- **Single-task IO** (like compio-quic): merge reader + writer in one select! loop, but completion-based IO isn't cancel-safe for reads
